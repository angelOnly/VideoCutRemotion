## 1. 实际实现了什么

### 1.1 正式导出：整片只绘制一次

原流程是 Remotion 先绘制整片，再把每个分镜重新绘制一次。新流程如下：

```mermaid
flowchart LR
  A[正式导出请求] --> B[冻结工程和输入]
  B --> C[Remotion绘制整片一次<br/>每视频最多5槽]
  C --> D[完整解码与实际帧数检查]
  D --> E[登记整片到readyFiles]
  E --> F[按原全局帧范围逐镜切分]
  F --> G[核验、改为正式文件名、登记]
  G --> H[生成整片＋分镜交付清单]
  H --> I[原发布流程再次核验并发布]
```

- 分镜使用原整片的 `[fromFrame, toFrame)` 区间，先准确解码选帧，再重新编码；音频按对应秒数裁剪并归零时间戳。不使用只能近似命中关键帧的流拷贝。
- 固定编码参数：H.264、CRF 18、fast、yuv420p、AAC 192 kbps；单视频逐个分镜处理，视频编码线程为 2，解码、滤镜和音频线程另有明确限制。
- 显式声明输出恒定帧率。真实短片测试曾发现缺少这一声明会使末帧时长错误，现已修正；没有放宽校验来掩盖问题。
- 检查尺寸、帧率、视频时间范围、音频时间范围，完整解码同时计算实际视频帧数，必须等于请求区间长度。视频时长只容忍封装精度误差；音频允许 AAC 包边界的小幅差异。
- 先写 `.pending.mp4`，核验成功后改名并登记；失败和取消清理该临时文件。
- 保持输出合同：整片在前，后面按照确认分镜顺序返回，正文、摘要、范围、规格和实测时长齐全。
- `previewOnly=true` 的动态片段仍按所选范围直接渲染。它不调用正式分镜续切逻辑，动态预览期间不能修改工作目录。

### 1.2 分镜失败后续做

新增 `retry_render_slices({renderRequestId})`。范围很窄：当前活动 Render Run、原正式导出明确失败、原整片已经核验，才能进入恢复。

服务重新核对原输入摘要、冻结工程摘要、模板规格，以及每个已登记文件的身份、位置、正文、摘要、实际帧数和音频范围。通过后跳过已完成文件，只补做缺失分镜，最后重建完整交付清单。

不会重新构建模板、重新绘制整片、重新配音或从作者当前工作目录取一版新工程。测试中已确认：工作目录修改不影响原快照续做，已完成分镜的修改时间保持不变；原整片或冻结工程被修改则拒绝恢复。

`unknown`、取消、终态 Run、局部动态预览、静帧批次、没有可靠整片的作业不能使用此入口。正在运行的原作业只返回原状态；记录为 running 但真实工作已不存在时返回 unknown。

### 1.3 批量静帧预览

旧 `preview_template_frame` 专用入口已删除，单张和多张都使用新接口：

```text
preview_template_frames({renderRequestId, frames: [0, 100, 200]})
  → 异步登记
  → read_render_job({renderRequestId}) 查询
```

每批接受 1～12 个不重复的全局帧号。先复制完整工程并核对复制前、复制后和副本的摘要；一致后才登记 `sourceDigest`。在这之前，作者应停止写入。

```mermaid
flowchart LR
  A[登记批次] --> B[复制并核对工程快照]
  B --> C[登记sourceDigest]
  C --> D[构建一次、浏览器一个]
  D --> E[原生renderFrames<br/>最多5槽]
  E --> F[原尺寸PNG及逐帧摘要]
  F --> G[分组概览]
  G --> H[关闭浏览器并清理临时构建]
```

图片结果保存在 `readyFrames`，保持请求帧顺序；视频仍保存在 `readyFiles`。图片不生成正式交付清单。概览每组最多6张，按请求顺序排布，原尺寸图保留用于中文细节检查。

同一批的并发完成回调通过串行队列写作业记录，避免原有固定 `.tmp` 文件发生重命名冲突或丢失已完成项。部分失败保留图片并列出 `missingFrames`；概览失败保留原图并返回警告，不重新绘制。

浏览器在成功、失败和取消后关闭；临时构建目录删除。工程快照和审片图片仍留在任务目录内，便于追溯，没有新加后台清理系统。

### 1.4 四任务容量和制作协作

沿用原有 `ProductionRunner → RunWork` 管理：最多4个活动 Run，每个视频最多5个绘图槽。正式导出、分镜切分、批量静帧、动态预览和固定媒体检查共用单视频入口，无法换编号同时启动第二项媒体工作。

作业输入摘要包含 `kind` 和完整输入；同编号同类型同输入返回原作业，不重复绘制。同编号不同类型或输入返回冲突。

任务指令与活动 Skill 合同一起更新：原作者交回可预览版及关键帧，独立审片集中列问题，原作者集中修改并说明影响范围，然后复查受影响位置及相邻切口。保留连续运动、声音检查和必要的多轮返修；没有改成“只准返修一次”。

## 2. 模板修复

长期维护源是整理器及其补丁文件，不修改历史冻结模板。新生成包为 **财经模板 2.0.2**。

- 片头只在真实 `[start, start + frames)` 区间出现，画面和声音使用相同长度，去掉导致区间外保持的调用。
- `intro.frames` 在模板类型中变为必填；运行时也检查正整数、起点、结束位置和与章节转场的冲突，不再默认67帧。
- 片头结束恢复原时刻的正文，不移动配音、字幕或全局图解时钟。
- 正文覆盖检查只排除真实片头区间；片头前钩子和片头后正文仍检查章节及图解覆盖。不能通过填写 `intro` 跳过整镜正文检查。
- 保持已有片尾开始时卸载正文的逻辑；允许正文保持帧位于“带片头的分镜”中，但不能落在片头区间。
- 提供两个小示例组件：SVG文字显式取消描边；动态数值按右侧对齐，并与单位保留间距。它们不是新的模板菜单，也不代替真实排版审查。
- 补丁锚点缺失或重复时停止。源码编译及生成后校验器的边界用例通过后才生成ZIP。

## 5. 失败处理和已知代价

1. **分镜经历一次额外有损编码。** 固定高质量参数减少损失，但不能声称无损；整片维持原渲染质量。此次合成样本的边界与声音检查不等于长片中文细节、渐变和真实听感已经验收。
2. **切分仍需CPU和时间。** 当前从整片开头解码到各分镜结束，不增加索引、跨文件帧缓存或无损中间片系统；实现简单，但越靠后的镜头会有重复解码成本。尚未实测生产服务器上的总收益。
3. **快照和图片增加磁盘占用。** 保留证据，没有引入自动删除策略；临时构建和浏览器会清理。
4. **技术验证不代替内容审查。** 片头片尾真实画面、文字可读性、连续运动及音频听感仍需新模板长片复测。静帧批量化也不保证作者一定减少返修。
5. **未知结果不能重放。** 进程消失、取消或记录损坏不会自动切换编号重做。恢复入口只处理当前活动Run内、原整片可信的明确失败。
6. **新旧接口需要成套切换。** 插件、Worker、工具Schema及制作指令应同版部署；旧会话和旧模板不能当成新版测试样本。
7. **构建取消有边界。** 模板构建库没有在这里新增强制中断机制；取消在构建返回后收敛，期间不提前释放单视频入口。没有声称实现全平台悬挂自动恢复。
