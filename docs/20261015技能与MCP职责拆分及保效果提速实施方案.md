## 一、是否会影响效果：目标、风险与判断标准

**本方案的目标是在保留声画设计和检查范围的前提下，减少重复计算、数据搬运、无关复查和模型等待。不能在开发前承诺实现绝对不会影响效果，必须通过明确的约束和对照验证证明。**

重点风险有三类：时间线装配算错或覆盖创作字段，导致声音与动作错位；复查范围缩得过小，导致问题漏查；自动交付选错版本或绕过技术核验，导致错误文件发给客户端。下文分别给出字段归属、版本绑定、失败处理和回归要求。

### 1.1 本轮必须保持的效果条件

- 保留确认正文、数字、顺序、音色选择、自然分段、作者明确的停顿及字幕阅读决定。
- 保留原有画质、帧率、画幅、完整 Composition、全局时钟、分块绘图和连续音轨策略。
- 程序不缩短动画、不统一改成淡入、不减少场景，不根据音频长度自动拉伸全部动作。
- 保留完整美术、演出、时机、字幕等专业方法；优化重复操作说明，不再压缩专业知识。
- 保留静帧真实观察、已发现问题的必要修复、受影响范围复查和自动技术核验；不以限制返修次数提速。
- 保留已有交付范围：静帧检查和必要返修后正式导出，技术合格后发布、回调。**不新增强制听审、连续观看门禁、人工审批或 Worker 待审状态。**
- 开发验证与生产交付均不新增试听任务；只记录实际完成的技术与视觉检查，不虚构听审或连续观看通过。

### 1.2 本轮不等于修好了动效不足

此前样片最后一个场景的主图持续约 331 帧，默认变化在 26 帧内完成；30 fps 下约 11.03 秒场景中，主图约 0.87 秒变化后保持约 10.17 秒。这是该图解层的源码行为，不代表字幕、背景等整幅画面完全静止。

当前专业方法已经要求跨句发展并诊断“动作结束后长时间只换字幕”。恢复正文不等于模型已经在作品里落实。上述现象应作为独立的创作质量问题保留；本轮先优化机械步骤，不能宣称提速顺带恢复了早期作品的动效丰富度。也不把“每帧都动”或像素变化比例当作质量标准，有阅读、比较作用的保持可以保留。

### 1.3 验证通过的含义

使用同一冻结工程、同一批真实音频和同一组创作决定，对照优化前后的时间边界、关键帧和音轨。技术等价与新作品的创意质量分别判断。两条模型重新创作的视频不同，不能只看总耗时就证明同效果提速。

## 三、职责合同

### 3.1 技能与代码分别负责什么

| 技能或负责人 | 保留的专业判断 | 程序接管的确定性操作 |
|---|---|---|
| `production-coordinator` | 真实分派、采用与意见冲突、原作者返修、选定正式交付作业 | 查询等待、状态归集、幂等登记、成功清单交接 |
| `production-director`、`scene-planning` | 章节与场面、观看发展、跨句关系、持续对象和接管 | 已确定场景的范围计算、结构覆盖、审片包归属 |
| `voice-production` | 自然分段、音色、速度、停顿、问题段是否重配 | 稳定 ID 接回、音频复制、测量读取、帧数换算 |
| `captions` | 语义换行、阅读单位、可靠依据下的分页 | 字幕绑定、句段边界装配、正文与越界核对 |
| `audio-finishing` | 音乐进退、压低、声音桥、音效落点 | 按设计执行合成、连续音轨与技术检查 |
| 美术、演出、时机、Remotion 相关技能 | 构图、中文排印、完整动作过程、落点、动画源码 | 受管引用、冻结、预览、渲染及派生时间事实 |
| `quality-verification` | 实际查看证据，判断布局、文字和图表表达问题 | 身份、分包、记录、连续领活、有效观察复用 |
| `export` | 明确交付版本，交回真实检查说明 | 正式范围推导、等待、技术校验、发布与回调 |

技能数量不等于代理数量。同一视觉作者可以承担美术、演出、时机和实现，同一声音作者可以承担配音、字幕和声音收尾。保留持续负责人，不因改动一个标签而重新分派全部角色。

### 3.2 唯一事实来源

| 事实 | 权威来源 | 不再要求模型重复维护的内容 |
|---|---|---|
| 当前正文、分镜 ID 与顺序、人物轮次、画面要求及制作参数 | 当前 Run 经服务核验登记的可信 `effectivePlan` | 各工具分别从旧请求或作者文件重选一版稿 |
| 原始输入与编辑来源 | 原始请求、对应 Analysis 和编辑差异 | 为适配执行结果改写原请求或请求摘要 |
| 音频身份、字节与实测采样 | 服务保存的成功 Speech Job | 自报音频路径、摘要和时长 |
| 当前作品时间线 | 声明合同的单一 `timeline.json` | 同时内嵌于 TypeScript 的第二份对象 |
| 静帧及观察结果 | 原媒体作业、SQLite 审片记录 | 手工 QA JSON 主状态 |
| 正式分镜范围 | 从冻结时间线推导并保存在原作业中的范围 | 模型再次抄写的 `ranges` |
| 交付文件清单 | 原正式作业的 `delivery.json` | 模型另写内容相同的 `result.json` |

沿现有 Run 检查点保存有效计划，不新增服务。首次 TTS 或媒体提交前由服务登记，绑定原 Run、原始输入摘要及对应分析版本；同内容重复登记复用原结果，已投入执行的计划不得被不同内容覆盖。正文、人物、声音来源及已确认制作要求发生实质变化时，沿既有修改任务机制处理。布局、字幕换行、动效接点、混音实现和技术修正等不改变上述依据的返修仍在当前 Run 内继续，只使实际受影响的媒体和检查失效。

配音、装配、字幕、预检、审片、正式导出与交付均绑定同一有效计划及摘要，恢复时读取原计划。`planRef` 仅补充尚未写入有效计划的停顿、字幕分页等装配决定；`timeline.json` 承载实际渲染数据和实测派生时间线，不成为另一份独立的语义计划。计划摘要用于版本绑定，不是要求所有 TTS 重生成的缓存键；未变文本、音色和速度且任务授权、音频身份可信时仍复用原声音。

## 四、单一时间线数据源与模板适配

### 4.1 当前与目标

此前核对的模板 `2.0.3` 中，`timelineModule` 指向内嵌完整对象的 `src/timeline.ts`，另有 JSON 供服务读取。目标是模板声明 `timelineDataRef` 与 `timelineContract`，渲染和服务使用同一份数据；开发时先核对最新模板与当前实现，不重复执行已完成的适配。

```text
renderer/timeline.json       当前完整时间线
renderer/src/timeline.ts    固定导入 JSON，并提供类型约束
动画组件                    读取上述时间线
装配、审片、导出            读取上述时间线
```

上述清单字段按最新代码的实际状态接续开发。服务只识别本次采用的时间线合同，不解析任意 TypeScript，不执行模板附带的任意脚本作为装配器。不支持此合同的模板明确报告能力范围，不自动猜测、转换或增加旧模板适配分支。

### 4.2 字段归属与写入边界

- 作者依据有效计划确定自然句段、停顿、字幕换行与可靠分页、章节分组；人物、音色、速度、正文和画面要求不得在装配计划中另行改写。片头按最新模板既有设置使用。
- 程序写入音频受管路径、实测派生边界、句段与字幕绑定、场景时长和已确定分组的派生范围。
- 作者保有 `visualBlocks`、动作事件、章节文案、`bgm`、`sfx`、包络和组件源码的修改权；装配不覆盖这些内容。
- 局部音频时长变化后，程序报告后续受影响范围。视觉作者负责重新校准动作、阅读和接管，不自动缩放全部动作。
- 章节的视觉起点与审片包覆盖范围分开计算。固定包装归入首末审片包；不能为通过审片而自动把作者 `chapter.from` 改为零，改变动画局部时钟。
- 章节分组需来自已确认的场景归属。不能可靠推导时报告具体字段，不猜任意场景内部切章。

维护入口为既有 `scripts/prepare-finance-template.py`、`scripts/patch-finance-template.py`、模板补丁和核验脚本；`.candidate` 只作证据或测试输入，不能成为新的模板维护源。适配后模板走正常发布流程，新任务采用新版本；旧冻结模板和历史成片不迁移。

## 五、声音基础装配与音频测量复用

### 5.1 `assemble_sentence_audio` 的接续调整

装配部分沿工作区已有的这个窄工具接续调整，替代每次现场编写的复制、测量、算帧和拼基础字段脚本，不另建重复装配工具。自然分段仍先由声音作者决定，配音继续使用现有批量接口。

输入结构示意；实际字段以最新 Schema 为准，本节补入的声源分类不能视为已经可用：

```json
{
  "assemblyRequestId": "audio_assembly_v1",
  "speechBatchRequestIds": ["speech_v1"],
  "planRef": "production/audio-assembly-plan.json",
  "expectedTimelineSha256": "当前时间线摘要"
}
```

时间线位置和 fps 从模板声明读取。`planRef` 只保存有效计划之外无法推导的装配决定，如 `gapBeforeFrames`、场景尾保留时间、字幕换行或可靠对齐引用、已确定章节归属的装配映射；不能覆盖有效计划中的台词、人物、音色、速度、顺序或片头设置。已经由批次明确且无变化的值直接复用，不强迫模型抄写另一份完整配音结果。音频正文、路径、摘要和时长从服务记录取得，并核对有效计划中的对应段落。

`speechBatchRequestIds` 允许合法的空列表，适用于本次有效计划确实没有 TTS 的情况。按实际片段和轮次处理声源，同一业务分镜可包含正文与内嵌片头：`tts` 必须找到对应成功音频；`template_audio` 读取最新模板原有资源、合法范围及既有声音设置，素材原本静音时不自动开启原声；`none` 必须有明确无口播依据，仅表示无口播，不排除 BGM。每个有台词且需要配音的段落仍必须具备真实 TTS，不能把配音缺失降格为无口播。零 TTS 仍执行模板、资源、画面、合法时长、场景顺序与覆盖检查，不意味着跳过装配或全部校验。片头不因此新增 TTS、网页分镜或口号处理逻辑。

执行顺序：

1. 核对当前 Run、有效计划版本与摘要、模板合同、正文、ID、声源及时间线基线。
2. 对需要 TTS 的段落确认批次完整成功，按稳定 ID 及确定顺序接回。缺段、重复段和正文改变明确拒绝；模板原声与无口播分别验证其实际依据。
3. 验证 TTS 源音频摘要，复制到受管 public。目标文件身份稳定，不覆盖另一份字节不同的旧音频；模板原声直接核对对应受管资源。
4. TTS 使用可信 PCM 测量，按 fps 换算足够覆盖的整数帧，加上作者指定停顿；模板原声与无口播场景按已确定的资产范围和合法时长装配，不能制造空白 TTS 凑时长。取整规则集中实现并验证边界。
5. 按实际声源生成所需 `utterances`、`captions` 和派生时间字段。有台词的字幕按有效计划和真实声音依据检查；无口播不强制制造字幕。没有可靠 `captionTiming` 时，TTS 沿用一段音频一张卡的现行合同，不能按字数比例虚构分页时间。
6. 保留视觉、音乐、音效和设计源码；报告真实时间差及需作者续接的范围。
7. 在受协调的写入阶段核对基线，以临时文件替换目标 JSON，保存装配输入和输出记录。

拟议输出示例：

```json
{
  "assemblyRequestId": "audio_assembly_v1",
  "state": "succeeded",
  "timelineRef": "renderer/timeline.json",
  "timelineSha256": "输出时间线摘要",
  "sceneCount": 9,
  "utteranceCount": 22,
  "timingChangedSceneIds": ["scene_003"],
  "detailsRef": "完整装配记录的位置"
}
```

同键同输入返回原记录，同键异输入拒绝。已装配后作者继续修改视觉，再调用原键只查回结果，不重新覆盖。装配中断后按原记录和实际输出摘要恢复，不新发 TTS。写入冲突返回真实差异；内存中的 Run 排他锁不能阻止作者直接编辑文件，因此还需协调暂停同文件写入及提交前后摘要检查，不能把锁说成完整文件系统隔离。

### 5.2 相同音频只测一次

此前核对的重复开销是 `DoubaoService.validateAudio()` 解码后，`verifySentenceAudio()` 又逐段解码。既有提速实现已在 Speech Job 中加入测量凭据，本次沿最新字段接续验证和复用，不新建全局缓存服务：

```text
音频摘要 + 测量规则版本 + 实际解码器标识
→ 采样格式、采样率、声道数、采样数量和时长
```

首次配音本地核验、装配和后续审计共用这份测量。解码器标识和固定参数来自实际执行环境，不能只写一个任意常量。测量缺失或规则变化时，按最新测量规则对原音频本地补测，不增加历史凭据适配或迁移分支。

每次审计仍检查当前批次归属、音频实际摘要、正文及顺序、字幕绑定、边界、可靠分页依据，以及检查前后工程是否变化。为当前源码摘要生成新的审计记录。**复用音频采样事实，不复用旧工程整体通过结论。**

音频字节不符先报绑定错误，不能当普通缓存失效后静默采用。取消、测量失败不能保存成功凭据；同 Job 并发补测合并执行。复用已有声音时继续验证任务授权、文本、音色、速度和实际字节，符合当前规则的测量直接读取，否则本地补测；有效计划其他字段变化不要求重新配全片。

## 六、公共前置检查与正式导出范围

### 6.1 前置检查由工具内部执行

提取共用时间线检查模块，统一读取当前有效计划并复用分镜范围、字幕和章节映射逻辑；不额外增加一个要求技能主动调用的重复检查步骤。

检查有效计划中的分镜 ID、数量与顺序，正文完整性，fps、总帧数、场景连续覆盖、资源引用、章节归属、片头片尾及静帧请求范围。句段和字幕边界按照 `tts/template_audio/none` 分支核验；删除“每镜必须有 TTS 和字幕”的统一前提，保留有台词且需配音段落的完整性检查。模板原声和无口播的资源、合法时长与覆盖同样必须通过。

挂接位置：装配提交前；静帧快照冻结后且 bundle/绘图前；正式导出快照冻结后且绘图前；`prepare_review` 读取映射时。检查是便宜的代码操作，冻结后仍须核对真实版本，不能因工作目录之前检查过就跳过。

删除服务之间重复维护的章节与范围转换实现，以及各入口直接从旧请求另选正文的逻辑。错误返回对象、字段、原因和修正方向；不自动修改作者的章节时钟、图形或正文。明确区分视觉章节与审片包对固定包装的覆盖范围。

### 6.2 正式导出不再手填 ranges

新公开合同区分两类输入：正式导出由服务推导全部范围，动态预览仍由作者指定 `ranges` 和真实疑点。建议从同一 Schema 生成两类参数校验，避免只写成宽松的“ranges 总是可选”。

```json
{
  "renderRequestId": "final_v1",
  "timelineRef": "renderer/timeline.json",
  "checks": ["实际完成的检查与未观察范围"],
  "previewOnly": false
}
```

登记原请求后冻结工程，调用现有 `sceneRangesFromTimeline()` 推导范围，保存为原作业的固定解析结果。bundle 后核对实际 Composition 的 fps 和总帧数；所有分块、合成和失败续做使用该固定范围。保留当前音频审计凭据和完整覆盖检查，删除新作业中“模型手填范围与服务计算范围相等”的重复比较。

原失败作业按其固定发行、快照和范围恢复，不从后来修改的工作目录重新推导。本轮不新增历史协议适配、旧 Run 迁移或历史数据改写；这不取消原作业身份与恢复的安全检查。

## 七、静帧精确复查与等待

### 7.1 保留章节上下文，按图片和检查目的复用

保留当前一章一份工作包、两个静帧检查目的和已有审片线程池，不拆成大量新任务，不增加审片存储系统。现有并行审片、原子领活、提交后自动下一包、幂等结果和旧凭证隔离继续使用。

当前 `reuse()` 的三个粗条件需替换：仅从整个已完成工作包取观察；一张图片有同类问题就否决整章同类复用；任意受影响 scene 命中章节就否决整章该项。新判断逐项落在 `checkId + evidenceId` 上。

必要的数据调整：

- 图片关联的真实 `sceneId`、帧位置由服务根据冻结时间线推导，不由作者自报。
- 工作包从当前有效计划提供正文、场景顺序及相关人物轮次、公司依据、画面指令和章节语义上下文。章节仍是理解单位，`remaining` 仅列必须重看的图片和检查目的。
- 复用保存原观察来源和成立依据。`partial` 中已正式保存的观察也可以复用，未看范围不能被补成完成。
- 未变证据上的问题与观察一起继承。变化证据的旧问题作为待复查线索，不能因新计划的问题数组为空就自动关闭。

复用必须同时满足：图片字节、尺寸、fps、帧号一致；检查目的与规则版本一致；场景/章节归属和相关语义上下文未变；相关依赖未变；原观察确实被服务接受。

| 变化或问题 | 复查与保留规则 |
|---|---|
| 同章另一张图片发生变化 | 不自动否决本图复用，继续核对本图相关依赖 |
| 字幕换行导致本图字节变化 | 本图相关检查重做；第一版不做区域差分，不能仅因改的是字幕就宣称同图其他观察可复用 |
| 图片相同，但正文含义、比较口径、人物轮次、公司依据、画面指令或章节关系变化 | 相关语义检查重新执行，不能只看 PNG 摘要；按真实依赖定位范围 |
| 音色、语速或声音来源变化 | 更新对应声音绑定与受影响时序检查；有效计划摘要变化本身不要求全片重新配音 |
| 未变图片有 blocking 或 warning | 问题与观察保留；观察完成不等于问题解决 |
| 未变图片有 suggestion | 建议保留可见，不强制返修，也不连带使无关图片失效 |
| 原工作包 partial | 复用其中满足条件的已保存观察，继续剩余范围 |
| 共享 TSX、字体或未知文件变化 | 保守扩大相关视觉复查，不相信作者口头声明 local |

第一版只缩小可以证明的变化，不建设通用 TSX 依赖分析或像素区域识别。章节比较、跨场关系、共享布局无法可靠分开时，仍按章节或全片扩大。单一 JSON 来源有助于减少纯数据修改被误判成共享源码变化，但不能消除所有全片复查。

### 7.2 `read_review` 有界等待

拟议输入：

```json
{
  "reviewId": "原审片编号",
  "afterDigest": "上次状态摘要",
  "waitMs": 60000
}
```

第一次无 `afterDigest` 时立即返回，之后等新观察/问题、剩余范围变化、完成、会话异常、取消、计划替换或超时。返回原摘要并增加 `statusDigest`、`timedOut`；摘要排除每次请求都会变化的当前时间等无关字段，避免无变化也被误判。

复用现有事件订阅方式：先订阅再读数据库，事务提交后通知。审片会话诊断也统一经服务更新并通知，避免只写数据库却不唤醒等待方。等待不持有事务，不占媒体额度，不放进全局工具串行队列；断开、取消、关闭时释放监听。事件不是状态真相，重连后从数据库读取。

超时返回当前真实状态，不把审片判失败，不重建计划。**这是有界等待，长审片仍可能需要少量续查，不宣称实现了完全零轮询。**

### 7.3 `prepare_review` 合并静帧等待与计划准备

拟议输入：

```json
{
  "renderRequestIds": ["frames_v2_a", "frames_v2_b"],
  "phase": "pre_export",
  "timelineRef": "renderer/timeline.json",
  "waitMs": 60000
}
```

主协调先提交本轮全部静帧批次，再直接调用此工具；无需先反复查询静帧，拿到结果后再组织一次准备请求。

服务检查指定编号是本 Run 已受理的原静帧作业，等待所有批次成功且同快照后创建一次完整计划。部分批次尚未结束时，超时返回 `waiting_media` 和 `pendingJobs`，不创建空计划，不虚构 `reviewId`。任一批次 failed/cancelled/unknown，返回原身份与诊断，不隐式重绘。相同参数重试查原作业，计划已生成时返回原幂等结果。

这一方案不建立持久化审片意图和后台补偿任务；调用超时或服务重启后需用原参数续准备。该代价换取更小的实现范围。多批次不能逐批替换活动计划，主协调不能边提交下一批边宣称本轮计划已完整。

## 八、正式成功后由 Worker 直接交付

### 8.1 调用链

旧成功路径中的重复步骤是：正式作业已生成完整 `delivery.json`，仍唤醒模型复制成 `result.json`，再返回 final。拟改为：

```text
主协调处理必要静帧问题，明确选择正式导出
→ render_template 登记原作业
→ 主协调返回 await_runtime，交出选定原作业
→ Worker 等待原作业终态
→ 成功：服务读取已有 delivery.json，保存正式交接
→ 原技术校验与 publishDelivery
→ 保存结果及唯一回调事件
→ 客户端接收
```

`await_runtime` 在新版运行合同中明确表示该正式作业是本次待交付目标，制作方没有尚需执行的独立创作步骤。成功后不再启动搬清单的模型轮次；明确媒体失败且需要判断恢复方式时才续接模型。

### 8.2 自动交付的身份条件

只能接回主协调明确选中的本 Run 正式 `template-render`、`previewOnly=false` 作业。等待记录中的执行次数、原始输入摘要、有效计划版本及摘要、源码摘要、发行和当前令牌必须匹配，任务未取消，作业成功且完整清单存在。清单的 task/run、模板、输入、有效计划、源码与作业身份逐项核对，路径受管。有效计划摘要不能覆盖原始请求摘要，两者分别承担追溯和执行版本绑定。

不能扫描目录里任意成功视频发布，不能把静帧、动态预览、另一执行次数或旧版本成片当作选定结果。保留主协调在正式提交时给出的真实 `checks`，不自动添加“已听审”或“全片连续观察通过”。不重新引入专业审片发布门禁。

### 8.3 实现和恢复顺序

扩充内部媒体状态类型，明确正式作业类型及 `deliveryPath`。执行控制器返回内部两分支：可交接的成功结果，或需要续接模型的明确失败。成功分支使用已有 final 交接形状，直接指向原清单，不再生成同内容的第二份结果文件。

在当前令牌和原等待记录仍匹配的短事务内，同时保存等待已转交及 handoff，防止重复终态或进程中断导致重复续接。内部等待检查点如需增加已交接标记，不改变客户端 Run 状态。

恢复时优先读取已有 handoff 或已由服务接管的等待：原成功作业直接恢复发布；可信的运行中作业继续原等待；无法确认的作业保留未知。当前“创作子线程恢复无法证明”的保护继续用于需要恢复创作的情况，不能阻断已经能够由服务确认的成功交付。

### 8.4 失败处理

| 情况 | 处理 |
|---|---|
| 正式媒体明确失败 | 返回原诊断给模型，按现有原作业续做或源码返修合同处理 |
| unknown、尝试次数或快照身份变化 | 保留原句柄核查，不创建新媒体掩盖未知 |
| 取消或令牌失效 | 不发布，不启动新的创作轮次 |
| 清单确定缺失、格式损坏、身份不符 | 明确结果错误，不让模型重写清单伪装成功；临时读取故障与确定缺失分开 |
| 发布时临时 I/O 失败 | 沿已有 handoff 恢复发布，不重配、不重绘 |
| 文件已发布但结果事务未完成 | 核对原发布目录和清单，继续既有幂等恢复 |
| 回调未被网页接受 | 重投原 outbox 事件，视频不重新生成 |

## 十一、保效果验证与性能记录

### 11.2 同工程对照

固定源码、真实音频、字体、资源、模板版本、fps、编码参数和实际渲染环境，比较：

- 正文、句段、字幕、停顿、章节和分镜全局帧界；检查首次与末次包装。
- 动作事件、持续对象、关键中途及跨场接点，尤其“后半场仍讲新关系但主图已结束”的既有风险。
- 相同渲染条件下的解码画面和音轨；小型隔离夹具可逐帧比较，完整工程选择风险帧和必要连续范围作技术对照。
- 正式分镜范围和整片覆盖，连续音轨与切片边界。

容器元数据或编码导致文件字节不同时，不能仅凭 MP4 哈希差异判效果变化；应检查解码内容和时间边界。反之，几个静帧相同也不能宣称全片运动和听感已验证。**上述音轨与连续范围对照是数据、解码和时序技术检查，不要求实际试听；开发验收和生产交付都不新增试听或连续听审门禁。** 报告只记录实际完成的技术与视觉检查范围，专业方法正文保留。

优先使用现有冻结工程和隔离目录完成工程等价与恢复验证，不把反复新建整片任务作为每项优化的默认测试方法。后续网页测试按实际授权与测试范围执行，其结果独立记录。

## 十二、后续故障排查表

以下定位项包含本方案拟新增的记录。未实施前应先检查实际版本，不能因为旧 Run 缺这些字段就认定数据损坏。

| 症状 | 优先核对证据 | 处理边界 |
|---|---|---|
| 动作提前结束或整体漂移 | 迁移/装配前后 scene、chapter、utterance 帧界，停顿、取整、局部时钟、动作事件 diff | 不为补审片包装而移动视觉起点；若为作者演出本身缺少后续发展，回原作者，不误报装配故障 |
| 字幕与声音错位 | 原 Speech Job、音频摘要、测量凭据、装配计划和输出、captionTiming | 不按字数估造时间，不先重新配全片；定位具体绑定或帧界 |
| 新台词或人物未生效，删除的内容又出现 | 原始请求、编辑差异、当前有效计划版本、各工具实际读取的计划身份 | 修正仍读取旧请求或装配文件自选正文的入口；不改写原请求摘要，不同时维护两套执行正文 |
| 纯画面或原声片头误报缺配音，有声段落反而漏配 | 有效计划的实际声源、台词、模板资产、TTS 绑定、时长与覆盖检查 | 合法零 TTS 仍走结构核验；需要配音的台词缺音频必须报错；不伪造 TTS，也不把整片静音 |
| 重复音频核验仍慢 | 实测规则/解码器标识、命中和补测原因、当前文件摘要 | 检查是否仍有无条件解码调用；保留当前绑定与字幕检查 |
| 应重查却复用了 | 图片身份、检查目的、有效计划中的正文/人物/公司依据/画面指令、依赖变化、复用来源 | 恢复受影响范围检查；相同图片不等于语义未变；不通过改严重度隐藏问题 |
| 一个改字导致整章或全片重查 | 单一 JSON 是否真正生效，TS 是否仍内嵌副本，实际失效原因和图片帧归属 | 修已知结构误扩大；未知共享代码仍保守，不删除安全依据 |
| 原问题在新计划消失 | 原 issue、复用链、新证据、待复查问题和最终处置 | 观察继承不等于问题解决，补回追踪，不默认关闭 |
| 审片一直等 | 当前计划、剩余范围、审片线程诊断、事件通知与超时摘要 | 部分观察继续保存；超时不重建计划；检查诊断写入是否发出通知 |
| 多批静帧审片不完整 | 本轮完整批次清单、每批状态和 sourceDigest | 等齐同版材料，不混版、不逐批覆盖活动计划 |
| 重复配音、预览或导出 | 原请求 ID、有效计划差异、段落文本/音色/速度、输入摘要、作业状态、装配/等待恢复记录 | 结果未知先查原任务；计划摘要变化不触发全片重配；不通过换编号重放掩盖恢复错误 |
| 视频存在但网页未收到 | 被明确选中的正式作业、delivery、handoff、发布记录、callback_outbox | 区分导出成功、发布成功、网页接受；只恢复失败环节 |
| 网页收到旧片或错片 | Run、attempt、源码/输入摘要、原 deliveryPath、发布副本摘要 | 检查是否错误扫描任意成功媒体；禁止通过重新生成掩盖身份错误 |
| 重启后停在未知状态 | 原发行、令牌、runtimeWait、handoff、媒体实际进程/终态 | 有可信成功交付先服务恢复；确需创作且子线程无法恢复时保持真实未知 |

每次排查至少保存版本、Run 与原作业身份、首次异常、原始响应、受影响范围和实际处理结果。不得在记录里保存账号密码、API Key 或会话凭证。
