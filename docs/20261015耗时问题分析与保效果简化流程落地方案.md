# VideoCutRemotion 耗时问题分析与保效果简化流程落地方案

日期：2026-10-15。

本文汇总本次对话中关于项目架构、技能与 MCP 分工、耗时原因、流程简化和开发落地的讨论。主要分析对象是 **VideoCutRemotion**，参考对象是 **ai-video-codex**。

**文档性质：问题分析与实施建议，不是开发完成、生产验收或性能提升报告。** 本次仅新增本文，不修改代码、技能、模板、发行物和生产任务。

## 一、先明确结论与证据边界

当前问题不能简单归结为“技能太简单”或“MCP 太多”。更值得处理的是：专业创作、机械执行、任务等待和异常恢复仍有交织，模型需要参与较多交接；首版作品出现问题后，又会触发返修、重新生成材料和复查。

建议遵循一条明确的开发边界：

> 模型给出创作决定，程序执行已经确定的操作，模型检查实际内容与效果。减少模型必须参与的机械交接，同时降低首版返修率。

### 1.2 不能从现有证据直接得出的结论

- 不能把导出前的全部时间称为无效等待，其中包含真实创作、检查和返修。
- 不能把历史独立审片进程的故障，直接认定为当前原生分派实现仍然存在的同一个故障。
- 不能把接口减少几次往返，直接换算成可以节省几十分钟。
- 不能把单元测试通过、媒体导出变快或检查记录收齐，分别等同于成片效果合格。
- 技能可发现数量不等于每次全文加载数量，也不等于实际代理数量。
- 本文不新增强制试听、连续观看、最终人工审批或 Worker 待审门禁。沿已确认的检查范围执行，明确记录实际观察与未观察的内容；需要判断动态或声音问题时，静帧本身不具备证明能力。

## 二、项目架构到底是从哪里看出来的

架构判断来自业务入口、技能、实际源码和运行记录的交叉核对，不是从某一份总览文档推导全部行为。

### 2.1 当前主要调用链

```text
网页提交文字、需求和模板
→ Analysis 生成可编辑的文字分镜
→ 用户确认本次完整分镜
→ Render 主协调读取当前确认稿和模板合同
→ 作者完成场面、视觉、声音及动画实现
→ MCP 调用当前 Run 的业务服务
→ 配音、时间线装配、预览和审片记录
→ 原作者按问题返修，按实际影响安排复查
→ 选定正式导出，交给 Worker 等待和执行
→ 媒体核验、发布、回调、网页播放
```

这是逻辑依赖，不代表每一步都严格串行。当前技能已经要求视觉、声音在输入具备时并行；不能将“增加并行要求”当成尚未存在的能力。

当前 MCP 主要是模型到业务服务的入口，生产工具通过内部 HTTP 调用相应服务。真正的媒体处理在业务服务和渲染器中完成。接口耗时不能一概归因于“MCP 协议慢”。

### 2.3 技能、参数字段和 MCP 的区别

- **技能**说明如何作专业判断，例如怎样组织场面、选择字幕阅读单位、检查转场。
- **参数结构**说明程序需要哪些输入，例如镜头编号、选帧、停顿、检查目的。
- **MCP 工具**让模型调用程序，例如装配配音、生成预览、登记检查结果。
- **业务实现**真正完成文件处理、时间计算、渲染、保存和失败处理。

| 常见字段 | 通俗含义 | 谁负责 |
| --- | --- | --- |
| `sceneId` | 哪个镜头 | 沿当前确认稿保持稳定，不每轮重编 |
| `frames` | 要生成哪些全局帧 | 模型选择检查位置，程序按帧绘制 |
| `planRef` | 作者决定文件的位置 | 模型提供业务决定，程序按公开结构读取 |
| `sourceDigest` | 这批材料对应哪一版工程 | 程序根据实际工程计算，不是美术评分 |
| `renderRequestId` | 哪个原媒体任务 | 提交后持续沿用，重查不换编号 |
| `evidenceId` | 哪份真实检查材料 | 程序生成并绑定实际文件 |
| `assignmentToken` | 当前是哪一代分派 | 程序隔离接替与迟到结果，不是审片者登录凭据 |
| `detailsRef` | 完整结果保存在哪里 | 程序保存，模型按需读取 |

技能入口很短，并不自动代表专业知识缺失：还要看是否引用了完整方法、作者是否实际加载、交付是否落实。相反，将所有参数规则和文件搬运步骤写成长技能，也不会替代程序实现。

## 三、耗时证据：为什么导出快了，整体仍然慢

### 3.1 0.1.20 完整复测基线

主要样本为 Render Run `81005bf8-902f-4f6b-bdfc-539264f0be16`，9 个镜头、27 段配音，4079 帧、30 fps，成片约 135.967 秒。

依据为 [完整复测记录](/Users/jiang/Downloads/ifeng/VideoCutRemotion/docs/20261015新版019职责拆分部署与网页两阶段验收.md)、[timing.json](/Users/jiang/Downloads/ifeng/VideoCutRemotion/docs/validation/20261015-web-020-repeat/timing.json)、[summary.json](/Users/jiang/Downloads/ifeng/VideoCutRemotion/docs/validation/20261015-web-020-repeat/summary.json)、[恢复记录](/Users/jiang/Downloads/ifeng/VideoCutRemotion/docs/validation/20261015-web-020-repeat/review-recovery.json)。

| 指标 | 实际记录 | 解释 |
| --- | ---: | --- |
| Analysis | 53.903 秒 | 不计入下面的 Render 耗时 |
| Render 到发布 | 53 分 30.635 秒 | 包含制作、返修、审片、等待和导出 |
| 正式导出前 | 47 分 25.441 秒 | 从 Render 开始到正式媒体作业开始 |
| 正式导出 | 6 分 2.074 秒 | 媒体作业区间，不是全流程 |
| 发布阶段 | 约 3.014 秒 | 与正式导出间另有很短交接间隔 |
| 两轮静帧生成区间 | 合计约 82.551 秒 | 首轮 19 张，第二轮 26 张；不包含模型审片时间 |
| 第二轮检查 | 52 项观察 | 26 张图片分别检查画面布局与字幕布局，不是 52 张图 |
| 审片查询 | 36 次，其中 30 次等待超时 | 不能将超时次数直接当作失败次数 |
| 人工干预 | 1 次 | 原独立审片进程长时间无响应后人工恢复 |

正式导出约占这次 Render 总耗时的 **11.3%**。在其他步骤完全不变的算术假设下，即使导出时间减少一半，也只减少约 3 分钟，总耗时约下降 5.6%。这解释了为什么继续优化单个媒体步骤，整体体验可能仍然很慢；该计算不是性能预测。

### 3.2 两个会掩盖局部优化收益的因素

**因素一：优化的步骤可能不在当时阻塞任务完成的路径上。** 视觉和声音可以并行，某一分支提前完成，不一定让另一分支、审片或交付更早完成。需要看“下一步究竟在等谁”，而不只是每个函数各省了多少秒。

**因素二：异常长等待和返修造成的波动，大于单项节省。** 本样本出现了审片连接恢复；上一轮也有类似人工处理。即使正常计算节省几十秒，一次十几分钟的无响应就会覆盖收益。首版错误越多，材料生成、问题交接和复查也越多。

对应处理顺序是：先验证当前审片路径能正常推进与恢复，同时把导出前时间拆清；然后降低首版返修；再合并机械工具操作。不能仅凭更高并发、更多审片者或更短提示词判断优化成功。

### 4.2 当前证据还缺什么

本地采集脚本 [collect.py](/Users/jiang/Downloads/ifeng/VideoCutRemotion/.candidate/web-020-repeat-20261015/collect.py)只保留了选定工具调用的最后 10 条到摘要中。摘要足以定位上述大区间，不足以还原全部作者活动、依赖等待和参数纠错。

因此本文不编造“导演用了几分钟、视觉用了几分钟”的精确占比。进一步归因需要原始 `logs/codex-events.jsonl`、`metrics/media.jsonl`、审片提交记录和原作业记录。

### 4.3 不另建观测平台，怎样得到可用结果

优先从已有事件配对出开始和结束。已有日志缺少关键关联时，只在真实业务边界补少量事件，建议表达以下信息，而不是增加模型需要填写的表格：

```text
发生时间
Run / 媒体任务 / 原生代理 / 检查单元编号
活动：创作、装配、材料生成、审片、返修、参数纠错、导出
事件：开始、有效进展、结束、失败、等待依赖、恢复
依赖对象：当前究竟等哪个产物或负责人
工程版本与原错误码
```

统计结果至少分成两张表：

1. **全流程时间表**：互不重叠的阶段区间，用于解释总耗时。
2. **各负责人活动表**：允许重叠，用于解释并行工作和依赖，不能直接相加冒充总耗时。

程序等待媒体、模型等待作者、模型没有响应、工具传输错误分别记录。缺少证据的区间标记为“尚未归因”，不能自动归入等待或推理。

分析最终要能回答：某个环节如果提前完成，正式导出是否也能提前？如果不能，当前阻塞它的另一项依赖是什么？

## 五、哪些流程可以简化，哪些判断必须保留

### 5.1 按职责拆，不按技能数量拆代理

| 环节 | 保留的专业判断 | 可以程序化的操作 | 简化方式 |
| --- | --- | --- | --- |
| 理解稿件和模板 | 主题、事实、表达目标、模板适配 | 读取确认稿、模板合同、版本身份 | 当前输入完整时不重复读取和改写同一份事实 |
| 镜头规划 | 章节、信息顺序、图形隐喻、镜头关系 | 保存稳定 ID、检查覆盖、派生已确定的时间范围 | 不让多个角色各自维护一套稿件 |
| 视觉与动效 | 构图、信息层级、动画过程、阅读节奏 | 稳定组件、文字测量、素材引用、编译 | 同一视觉作者连续负责设计、实现和返修 |
| 声音与字幕 | 自然分段、语气、停顿、语义换行、可靠分页 | 配音批量提交、文件绑定、实测时长、帧计算 | 使用现有装配能力，减少现场脚本和手算 |
| 审片准备 | 看哪些位置、采用什么材料、检查什么 | 固定版本、绘制、登记真实材料和进度 | 整轮检查材料一次提交，内部完成机械步骤 |
| 审片 | 实际观察、判断问题、说明范围 | 保存观察、统计缺项、隔离迟到结果 | 默认返回简洁状态，按需取详情 |
| 返修与复查 | 根因、修改方式、语义影响、复查范围 | 提供文件与时间线差异、生成材料 | 原作者修受影响部分，保留仍有效的工作 |
| 正式导出 | 选定交付版本、真实检查说明 | 冻结、导出、技术核验、发布和回调 | 继续使用已有 Worker 直接交付路径 |

### 5.2 可以试验的角色安排

对本次讨论的财经模板任务，可以试验以下职责归并：

| 承担者 | 持续负责的内容 |
| --- | --- |
| 主协调兼导演 | 当前完整稿、场面关系、实际分派、意见取舍、返修范围 |
| 视觉作者 | 美术、动效、Remotion 实现和视觉返修 |
| 声音作者 | 配音表达、停顿、字幕时序和混音 |
| 按需独立审片者 | 对指定真实材料做独立观察，回传具体问题 |

这是待验证的组织方式，不是必须固定四个代理。输入简单、角色相邻时可以兼任，但持续负责人、未完成产物和回传时机必须清楚。

当前制作入口仍要求建立持续负责的导演。主协调与导演合并需要同步修改入口和真实分派方式，不能只在文档里改名字。独立审片是否保留、保留多少，应结合已确认产品范围和实际质量收益，不通过一刀切取消审片证明提速。

### 5.3 不应该省掉的内容

- 对当前确认稿、人物、数字、顺序和实际素材的理解。
- 场面表达、语义分组、布局和动作设计。
- 对实际生成材料的必要观察，以及已发现问题的处理。
- 真实音频和媒体身份、时间范围、文件完整性的技术核验。
- 源码变化后的影响判断，尤其是跨镜头对象和共享组件。
- 未完成、失败、未知和已完成状态的真实区分。

不能靠降低清晰度、统一改成简单淡入、删正文、任意限制返修次数或减少必要观察来证明同效果提速。

## 六、一个已经实现的拆分范例：配音装配

### 6.1 模型决定什么

例如模型决定：镜头 3 有两句话，第二句话前停顿 6 帧，口播结束后画面保留 12 帧。语义换行和需要的字幕分页也由作者决定。

模型交出决定，调用已有 `assemble_sentence_audio`。其输入由当前 Schema 定义，包含装配请求编号、配音批次引用、计划文件和时间线基线摘要。

### 6.2 程序已经负责什么

在 [sentence-audio-assembly.ts](/Users/jiang/Downloads/ifeng/VideoCutRemotion/packages/production-service/src/sentence-audio-assembly.ts) 中，程序接回成功配音，验证正文和身份，读取实测时长，按帧率计算边界，加上作者指定停顿，生成音频绑定与派生时间字段，写入单一时间线，并返回 `timingChangedSceneIds`。

这部分保留视觉与声音设计，不自动替作者决定图表怎样演进，也不为了适配时长而删稿。音频变长影响了阅读或动画接点时，模型再调整相应表现。

### 6.3 这说明怎样“拆出来”

```text
作者决定：两句话之间留 6 帧
程序计算：音频 A 结束帧 + 6 → 音频 B 开始帧
作者判断：实际播放后，这个停顿是否合适
```

模型保留决定权，程序承担准确执行。其他机械链路可以按同样方式拆分，不需要从头建立一个通用流程系统。

历史 0.1.19 曾因 `planRef` 内部结构没有充分公开，导致参数猜测和纠错；0.1.20 已从现有 Zod 定义生成同源说明。这个问题说明接口合同需要完整、同源，而不是要求模型记住更多猜测规则。不要将已修正的缺口重复列为待开发功能。

## 七、第一个建议落地的完整切片：整轮审片材料一次准备

### 7.1 当前操作为什么繁琐

当前 `preview_template_frames` 一次最多 12 帧；一次 26 帧检查通常要拆成多个请求。每次 `templateFrames()` 都冻结一份工程，随后准备渲染环境、绘制并保存图片。当前已有编译缓存，不能把多次调用等同于每次都完整重新编译。

模型还需要搬运多个媒体任务编号，将检查目的与实际图片对应，再调用 `prepare_review`。审片服务会拒绝混合源码版本的材料。

如果只写一个包装函数连续调用三次旧静帧接口，仍然是三次独立冻结。作者在中间修改工程时，材料可能属于不同版本，核心问题没有解决。

### 7.2 新的业务边界

模型一次提交本轮检查决定。以下仅是业务示意，不是已发布参数：

```text
本轮：第二轮场面检查

检查项 A
场面：镜头 3
材料：全局帧 3010、3020、3030
目的：旧标题退出时是否与新标题争用同一区域

检查项 B
场面：镜头 4
材料：作者选择的若干全局帧
目的：字幕出现后图表标签是否仍可读

其余检查项……共 26 张图片
```

作者仍决定检查目的、材料类型和位置。程序不自动发明“已经检查过”的结论，也不根据图片数量推断审片完成。

### 7.3 程序内部怎么完成

```text
受理一个媒体任务并保存检查计划
→ 冻结一次工程，保存工程摘要
→ 准备一次渲染环境
→ 按现有资源预算生成全部指定图片
→ 每张成功图片落盘并登记帧号、路径和摘要
→ 媒体完成后，依据原检查计划补齐真实材料引用
→ 调用已有审片服务登记检查计划
→ 返回审片编号、进度、异常与完整结果引用
```

是否内部按 12 帧分批，应依据资源限制决定，不必将旧工具参数上限当作渲染引擎的必然限制。如果保留分批，所有批次必须使用同一个快照、Composition 和渲染环境，不能重新调用会冻结工作目录的外层函数。

可沿现有预览入口扩展“用于本轮审片的完整计划”语义。临时创作预览仍有独立用途；针对整轮审片的旧拆批和搬运步骤退出技能流程，不叠加第二套同义审片协议。正式参数名称应与实现一起确定，本文不发布虚构工具。

### 7.5 必须说明“已受理”和“已冻结”的区别

当前入口可能在真正冻结之前返回已受理。静帧任务排队期间，工作目录仍可能改变。

建议使用已有 `onSourceFrozen` 通知表达清楚：

- **等待冻结**：本次版本尚未固定，作者暂不修改待冻结工程。
- **已冻结**：返回真实 `sourceDigest`，后续材料绑定该快照；工作副本可以继续修改。

若调用方明确指定先前版本，应核验该版本并在不一致时拒绝，不能静默采用最新工作目录。源码摘要只证明版本身份，不证明画面好看。

### 7.6 失败怎么处理

| 情况 | 处理方式 |
| --- | --- |
| 中间绘图失败 | 保留快照和成功图片，报告缺少哪些帧，不能报告材料全部完成 |
| 图片成功、登记审片失败 | 保存媒体成功事实，只恢复登记，不重新绘制 |
| 重复同一请求 | 同编号同输入返回原任务；不同输入明确报冲突 |
| 原任务状态未知 | 查原作业，保留诊断，不换编号偷偷重做 |
| 源码或图片身份变化 | 拒绝混合采用，报告实际版本冲突 |
| 任务取消 | 停止后续工作，保留已完成产物和真实状态 |

媒体成功和审片材料登记成功是两个结果，可以在原媒体作业 JSON 中分别记录，不必加新表。重复登记应回到同一份检查计划。

现有正式导出续切不等于静帧续绘。第一版若不支持缺帧续绘，应明确保留产物并报告失败；若实现续绘，则另行验证始终使用原快照，不能凭借“已有恢复接口”宣称已经支持。

### 7.7 少量高价值验收

1. 固定同一工程、字体、环境和帧号，新旧路径生成的解码后像素一致；确定性夹具也可比对摘要。
2. 冻结后修改工作副本，后续图片仍来自最初快照；冻结过程遇到并发修改不能静默接受。
3. 模拟中途绘图失败和登记失败，成功产物保留，不误报完成，不无意义重画。
4. 重复提交不创建重复媒体或检查计划。
5. 隔离真实任务记录模型请求次数、交接次数和墙钟时间。只能报告实测收益，不承诺消除历史几十分钟停滞。

## 八、“先验证审片恢复”具体是什么意思

### 8.1 历史问题是什么

0.1.20 样本中，已有 38 项观察入库，剩余 14 项未完成。独立审片进程长时间没有响应，最终人工处理了该子进程。原计划、音频、图片和已完成观察都被保留，接替者完成剩余范围。

这证明当时能够在人工帮助后恢复，不证明无需人工干预。历史 `SIGTERM` 是故障证据，不应变成新架构的常规操作步骤。

### 8.2 当前实现已经改变了什么

根据 [职责拆分开发验证记录](/Users/jiang/Downloads/ifeng/VideoCutRemotion/docs/20261015Codex与Worker效果职责拆分开发验证.md)及当前源码，独立审片会话池已被移除；主协调通过宿主原生代理分派审片，Worker 保存材料、进度、观察和真实差异，不自行启动审片模型或自动领下一包。

当前已有显式分派、部分观察保存、接替代次、迟到提交隔离、显式静帧复用等基础。这些不需要重新开发一套。

### 8.3 还需要验证哪些行为

| 场景 | 应验证的结果 |
| --- | --- |
| 正常审片 | 持续有真实进展，完成后进入后续制作，不需要人工杀进程 |
| 审片者提交一部分后退出 | 已完成观察保留，接替者只处理剩余检查与未关闭问题 |
| 旧负责人迟到提交 | 不覆盖新分派，不让旧版本结论变成当前结论 |
| 媒体或调用等待超时 | 继续查询原任务，不重生成音频或静帧 |
| 主会话或宿主异常 | 明确能恢复到什么边界；不能将子任务接替等同于整棵创作会话都可恢复 |

建议先做隔离的部分提交与接替验证，再做正常完整任务。故障注入只作用于验证任务，不拿生产任务反复中断试验。

### 8.4 为什么“定时查询”不等于已经解决

当前会话代码定期保存诊断，工具观察器能够标出长时间未结束的调用；这些是诊断能力，不是每个审片单元都具备自动恢复能力。

需要区分：收到通信事件、调用仍存活、实际观察完成。查询次数增加不算业务进展；一个检查单元不断提交，也不能掩盖另一个单元停滞。

如实测仍有长等待，优先利用现有分派和提交记录，关联单元负责人、最后有效观察、最后宿主事件和当前未完成范围。在确认异常后，由原协调路径决定续接或接替，并记录原因；不能只依据一个固定静默时长就自动重开整轮审片，更不应恢复已经删除的独立会话池。

## 九、为什么排版和过渡会反复返修

### 9.1 模板不等于所有画面已经固定

财经模板有固定包装，但本期图形和动画仍允许作者编写。内容长度、图表结构、强调数字和镜头关系每期不同。稳定包装不会自动保证新写的内容层没有问题。

现有验收记录包括 JSX 标签未闭合、音乐资源路径错误、文字与线条干扰、标签重叠等。它们应分别归为工程错误、资源绑定问题和画面设计问题，不能全部叫作“排版差”。

第 3020 帧的问题更具体：新标题与旧标题占用相同区域，旧图表内容在新图后残留。它涉及退出与进入时机，单纯改字号可能无法解决。该证据只说明这一帧的问题，不能从一张图推断冲突持续多久。

### 9.2 如何把重复工作做成程序能力

| 类型 | 稳定代码承担 | 模型继续承担 |
| --- | --- | --- |
| 标题与数值卡 | 字体、边距、对齐、稳定区域、真实文字测量 | 信息层级、强调对象、布局选择 |
| 字幕 | 沿可靠时间依据定位，执行作者换行和布局规则 | 语义分组、必要分页与阅读判断 |
| 图表标签 | 通用标签排布和已声明的禁入区域检查 | 图表表达方式、具体取舍 |
| 转场 | 统一承载进入、退出和局部时间边界 | 对象如何接管、何时交叠、跨镜头关系 |
| 工程正确性 | 编译、资源存在、范围和数据结构检查 | 对失败原因的设计修改 |

项目已有 [字幕布局工具](/Users/jiang/Downloads/ifeng/VideoCutRemotion/packages/remotion-runtime/src/caption-layout.ts)和 [财经视觉补丁](/Users/jiang/Downloads/ifeng/VideoCutRemotion/scripts/finance-template-patches/safe-visuals.tsx)，应先确认实际模板采用情况再扩展。工具存在不代表当前所有模板都已接入，也不代表已实现通用自动排版。

程序发现越界，应返回对象、区域和测量结果。不能持续缩小字体、删文案，或把所有几何交叠都认作错误；设计中可能存在合法的叠放与遮罩。

### 9.3 降低“改一处，全片重查”的实际方法

- 将稳定共享组件与单镜头实现分开，使镜头 3 的局部调整尽量不改全局文件。
- 对确实跨镜头持续的对象，明确由共同父层负责，不为实现局部修改而破坏全局时钟和连续关系。
- 先检查最能暴露问题的代表性场面与高信息密度场面，再推广相同设计；当前技能已有相关方法，应检查是否落实，而不是继续重复添加文字。
- 同类问题按根因修组件或时序规则，避免每张图重复补坐标。

当前 [review-invalidation.ts](/Users/jiang/Downloads/ifeng/VideoCutRemotion/packages/production-service/src/review-invalidation.ts)只提供文件、场景和时间线变化事实，专业影响由模型决定。不要把旧实现的“共享文件变化导致全量失效”当成当前服务仍自动执行的规则。

局部复查应看实际影响：改标签检查该镜头；改退出动画检查相邻衔接；改共享字号检查相关使用者。画面字节相同也不自动证明语义关系不受其他变化影响。

## 十、怎样具体减少工具往返

### 10.1 合并相邻的机械步骤

优先合并不需要中途再次作专业判断的操作，例如本轮选帧后的冻结、绘制、整理与登记。需要模型实际观察后才能决定的下一步不能预先替它执行。

不必把所有制作包装成一个万能工具。完整业务边界比工具数量更重要：一个工具如果仍返回大量零散材料、要求模型反复猜下一步，数量减少也不代表交接减少。

### 10.2 默认短状态，完整信息按需读

配音和媒体已经通过 `tool-results.ts` 提供摘要及完整结果引用，可以沿用。当前 `read_review` 仍会包含完整检查单元、观察和多份相关列表；无变化超时时也会返回完整内容。

建议默认表达以下信息，字段名以实现时同源 Schema 为准：

```text
当前检查计划与工程版本
需要观察 52 项，已完成 38 项，剩余 14 项
本次是否有新进展
新增问题或异常
完整材料引用
```

单元详情、完整证据、原始诊断按需读取，不能为了短输出丢失关键异常、待处理问题或恢复依据。已有 `afterDigest/waitMs` 有界等待可以复用，不另建轮询服务。

### 10.3 正式导出等待已经交给程序

当前 `await_runtime` 与 `ExecutionController` 已经支持选定正式媒体作业后由 Worker 等待，成功采用原 `delivery.json` 进入交付。明确失败才回到模型判断；未知状态不重放。

不要再要求模型不断查询成功导出、手抄清单或额外写一个相同的结果文件，也不要把这项已实现能力重新算作新方案的全部收益。

### 10.4 技能与接口应一起更新

技能保留“何时调用、需要什么创作决定、怎么看结果、失败如何判断”。业务服务承担固定文件操作、派生字段、任务状态、幂等与结果归集。

维护源是 `.agents/skills/`，修改后沿现有 `plugin:sync-skills` 生成发行视图。避免同时手改维护源、发行副本和文档中的多套字段说明。公开参数和校验尽量来自同一份现有 Zod 定义。

## 十一、怎样验证效果与速度，而不是只看测试通过

### 11.1 两种验证分开

| 验证类型 | 固定什么 | 能回答什么 |
| --- | --- | --- |
| 确定性执行对照 | 同工程快照、音频、选帧、字体、环境和输出规格 | 程序改造是否改变画面、时间边界或产物身份 |
| 真实制作对照 | 同稿件、模板、模型设置、运行环境和交付要求 | 流程和角色变化是否改善完整任务体验与作品问题 |

两次模型重新创作的画面可能不同，不能要求所有像素相等；机械执行等价则应尽量使用同一冻结输入验证。两个问题不能混用一个指标回答。

### 11.2 每轮保存哪些条件

使用现有验证目录和日志记录：代码提交及工作区状态、Release、模板摘要、确认稿、模型和思考设置、依赖、字体、编码器、机器、并发任务、输出规格、是否已有缓存和原 Run 身份。

冷缓存和已有缓存分开报告，不能让新版本使用热缓存、旧版本使用冷缓存再归因于代码提速。模型额度和外部服务故障单独注明，不隐去失败样本。

### 11.3 建议的最小验证流程

1. 保留当前可解释基线，在隔离环境验证一个改动，其他条件保持一致。
2. 对确定性改动做少量核心回归：同版材料、重复提交、部分失败、结果登记失败和取消。
3. 通过后，以固定稿件和模板重复跑完整业务；建议每版至少 3 次作为初步观察，报告每次结果、中位数和最慢值。
4. 样本少时不包装成可靠 P95 或稳定提速百分比。波动仍大就保留结论限制，继续针对长等待查证。
5. 检查实际作品问题及返修记录，之后再决定是否扩大使用。

### 11.4 对照表至少包含的指标

| 指标 | 为什么需要 |
| --- | --- |
| Analysis、Render、导出前、正式导出、发布耗时 | 避免总耗时与单项耗时混淆 |

## 十二、可以直接拆成开发任务的实施顺序

### 12.1 先完成基线与恢复验证

**目标：** 确认当前版本的原生审片能够推进和接替，补齐导出前时间归因。

**工作：** 沿已有日志、分派和提交记录核查；必要时补最少的业务事件；做部分提交与接替验证及完整任务复测。

**交付：** 实际版本、可复核时间表、人工干预记录、未归因区间和恢复边界。不仅交一份测试通过截图。

### 12.2 任务 A：整轮审片材料一次准备

**目标：** 减少拆批、冻结、任务编号搬运和登记交接。

**范围：** 本文第七节列出的媒体入口、渲染器、审片服务、结果摘要与技能更新。保持原创作决定、选帧、画质与检查目的。

**退出的旧操作：** 模型自行拆 12 帧、重复收集批次编号、重新拼同一轮材料对应关系。不删除有独立用途的临时预览能力。

**验收：** 结果一致、固定版本正确、失败保留产物、重复请求不重复执行、真实往返减少。已知代价是业务入口需要承担材料登记状态，不能只靠媒体任务一个成功标志。

### 12.3 任务 B：审片结果摘要和等待交接

**目标：** 少读重复信息，保留完整事实与恢复依据。

**范围：** `review-service.ts`、`tool-results.ts`、工具声明和相应技能；复用已有有界等待。

**退出的旧操作：** 每次无变化仍完整搬运全量观察，模型反复整理相同计数。

**验收：** 摘要与完整记录一致；问题、剩余项和异常不遗漏；观察状态改变能及时读到。它不单独解决模型无响应。

### 12.4 任务 C：反复返修的模板组件和转场

**目标：** 降低首版问题和修改扩散。

**范围：** 真实出现问题的标题、数值卡、图表标签、字幕区域、场面进入退出；优先复用现有布局工具及模板维护脚本。

**退出的旧操作：** 每期重复手写相同布局、同类问题逐帧补坐标、局部修改无必要地改共享源码。

**验收：** 固定高信息密度稿件，首版问题减少；没有靠删字、缩成不可读字体或简化动画掩盖问题。已知代价是组件设计需要处理真实内容差异，不能强行把自由场面全参数化。

### 12.5 任务 D：角色合并与复查范围试验

**目标：** 降低专业角色之间的重复解释与等待。

**范围：** 协调入口、真实代理分派、持续负责人和交接方式。模型依据程序提供的差异决定复查，不新增自动语义失效引擎。

**退出的旧操作：** 相邻职责重复建立作者、每次小改重新分派全部角色、重复传完整历史。

**验收：** 与前述任务完成后的基线单独比较，交接减少且首版、最终问题不增加。已知代价是单个作者承担更多职责，需要防止上下文负担和自查盲区。

### 12.6 为什么分开实施

不要同时更换模型、模板、协作结构、检查范围和媒体执行，再用一次快慢结果解释全部变化。每个任务保持可独立验证；通过后再推进下一项。

每次正式实施应同步更新代码、接口、技能和少量核心测试；生成候选与部署、生产验证分别记录。本文不执行上述开发或部署。

## 十三、ai-video-codex 可以参考什么

参考项目的 [视频剪辑技能](/Users/jiang/Downloads/ifeng/ai-video-codex/plugin/skills/video-editing/SKILL.md)区分规划和执行：规划理解实际素材，形成方案；确认后的执行读取确认方案，不重新规划。

其 [MCP 入口](/Users/jiang/Downloads/ifeng/ai-video-codex/mcp/server.ts)与 [RenderService](/Users/jiang/Downloads/ifeng/ai-video-codex/media/render.ts)让模型提交成片编号和必要的表达决定，后端自行读取已确认方案、处理实际媒体与产物。

值得借鉴的是：

- 清楚地区分方案、确认和执行。
- 工具绑定当前任务，减少模型重复传递已知事实。
- 模型表达业务意图，程序完成底层媒体操作。
- 对真实音频、素材、确认稿和结果保持明确来源。

VideoCutRemotion 允许更自由的 TSX 场面与动画创作，不能照搬参考项目较窄的素材剪辑流程，或用技能长度直接衡量设计优劣。可以借用职责边界，同时保留场面设计、动作关系、必要观察和局部返修。

## 十四、实施时需要持续保持的边界

- 已确认稿和实际有效制作输入只有一个权威来源，原始输入用于追溯；不能让作者计划再解释一版正文。
- 程序管理任务、版本、时间计算、材料与交付，模型管理表达、效果判断与修改。
- 同一原任务的重查不创建新任务；明确失败与结果未知分开处理。
- 已有音频、图片、快照和有效观察尽量沿原身份保留，不因协调恢复重做全部制作。
- 对受影响内容重新检查，保留已发现问题直到有真实处置依据。
- 不用新增通用引擎、角色池、兼容层或多套计划对象解决当前可在现有模块内完成的工作。
- 每项优化都说明实际减少了什么、保留了什么、如何验证，以及仍然解决不了什么。

本次文档交付完成后，仍需通过实际开发与对照实验验证提案。尤其是审片长等待、首版返修率和角色合并收益，不能在文档阶段作出已解决的结论。
