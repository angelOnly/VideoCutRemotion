## 二、输入与分镜怎么改

### 1. 两栏一起理解

- 两栏至少一栏有实质内容，保留原始输入。两栏都可以包含稿件、人物台词、画面说明或修改要求，不按输入框决定文字用途。
- Analysis 区分实际台词、说话人、章节、画面指令及其他要求。例如 `【财小策 提问】` 用于确定说话人，`【室长 亮相】（室长出镜）` 用于安排画面，标签本身不进入配音。
- 明确“第三段改成……”时按修改要求处理；重复、替换和参考内容说明采用关系。普通台词中的括号不能统一删除，也不得擅自改写财经数字或补造问答。
- 替换当前“所有分镜正文拼起来必须等于原始 `content`”的检查：检查实际台词是否完整采用，导演说明是否保留在对应字段，明确替换或舍弃的内容是否有依据。保留原字段与对应片段位置，便于排查遗漏。
- Analysis 仍只输出可编辑分镜；只有制作要求、缺少可采用内容时，指出具体缺项。

**具体实施：**

1. **入口校验一起改。** `analysisRequestSchema` 与 `normalizeWebAnalysis()` 都允许单栏为空，统一检查 `content.trim()` 或 `otherRequirements.trim()` 至少一个非空；原始字符串不做全局裁剪，保留后续来源位置。沿用现有长度限制，不把需求栏复制成假正文来通过校验。
2. **一次解析产出可用分镜。** 同步修改 `task-instructions.ts`、Analysis 技能和模板的 `文字分析合同.md`，让本次 Analysis 在原有结果中输出台词、人物、画面指令及采用依据。角色信息从模板已有文字说明提供，Analysis 不加载制作源码、不开始配音。
3. **保留可检查的来源。** 在原 Analysis 结果中记录输入字段、原文起止位置、用途及对应分镜/发言；被明确替换、重复或仅作参考的内容附处理说明。编辑后新增的台词以当前提交为准，不强行匹配旧稿。无需新建来源服务或数据库表。
4. **替换检查，不直接删掉保护。** `ProductionRunner` 接收结果时继续校验身份和分镜 ID；将全文拼接判断改为来源范围、引用目标、实际台词及采用关系的检查。结构错误或无依据改字返回具体字段/分镜。程序检查引用与文字是否相符，语义分类仍由 Analysis 负责，不宣称字符检查能证明导演理解正确。
5. **结果完整回传。** `analysisResultSchema` 和网页回调保留新增字段，前端据此展示和编辑；`dur` 仍是估时，真实时长继续由后续制作获得。

例如输入 `【室长 亮相】（室长出镜）今天拆浩欧博。`，Analysis 应得到“台词：今天拆浩欧博。”“人物：室长”“画面：室长出镜”。检查针对这三部分各自的采用位置，不再要求配音正文包含标签。

### 2. 在现有分镜上保留必要信息

继续使用 `dataList` 和原有 `id/content`，在分镜中增加 `directing`，保存说话人及画面指令。建议结构如下，具体字段在现有接口中统一定义：

```json
{
  "id": "scene_001",
  "content": "今天拆浩欧博。",
  "directing": {
    "kind": "speech",
    "speechTurns": [
      { "id": "turn_001", "speakerId": "shizhang", "start": 0, "end": 7 }
    ],
    "visualDirections": ["室长出镜，展示企业概况"]
  }
}
```

- `content` 保存实际台词；`speechTurns` 表达本镜谁说哪一段，支持同镜多人发言；指定人物映射到模板已有音色。未指定的 `speakerId` 可为空，由导演沿用模板规则安排；已指定人物不再按问句或段落位置重新分配。
- `start/end` 为本镜台词的 UTF-16 半开区间。改字、拆镜或合镜时同步调整范围和人物归属，服务检查范围有效、没有重叠和遗漏；不能拿旧偏移套新台词。
- 制作时将人物发言对应到现有配音句段和人物状态。一轮发言可以对应多个句段，不重做配音批次、语速或音频复用机制。
- 明确无口播的画面可以没有台词，但须有画面安排及合法时长。模板片头可继续按原方式嵌入，不强制增加网页分镜。

**字段与编辑规则：**

| 数据 | 放在哪里、谁负责 |
|---|---|
| 实际台词 | 沿用 `scene.content`；前端保存当前编辑值，后续配音与字幕对照这一份正文 |
| 人物与发言顺序 | `directing.speechTurns`；Analysis 初次生成，前端编辑时维护，导演按指定人物安排表演 |
| 画面动作 | `directing.visualDirections`；导演和模板作者消费，配音请求不拼入此字段 |
| 是否有口播 | `directing.kind` 区分 `speech` 与明确的 `visual`；`speech` 必须有台词，`visual` 必须有画面安排 |
| 无口播展示时长 | 在 `directing` 中保存明确的 `durationSec`；只有无口播画面使用，不能用它替代口播的真实配音时长 |

在现有分镜编辑区显示人物和画面说明，不增加新的制作阶段。单人镜改字后重算该轮次范围；多人镜按发言轮次编辑，再由前端统一生成 `content` 和对应范围。重排保留场景及轮次归属，拆镜/合镜同步带走对应轮次，不按句子顺序重新猜人物。服务再做同样的结构校验，避免界面漏传或偏移失效。

**制作衔接的具体改法：**

1. 导演读取 `speechTurns`，将每轮台词拆成现有自然配音句段，用现有 `sceneId/segmentId` 关联。句段不跨越两个人物的发言边界，角色选用模板已有 `finance.female/finance.male` 音色。
2. 模板适配层建立“人物发言 → 句段 ID → 音色”的对应关系，句段 ID 继续作为 `utterance.id`。装配和句段核验按当前分镜中的发言顺序对照正文、人物与音色，保留人物字段；无需另加一套配音 API 或修改供应商协议。
3. 当前模板的 `SpeakerStage` 只读 `scene.speaker`，不能表达同镜换人。最小改法是在模板句段上补 `utterance.speaker`，按真实 `startFrame/endFrameExclusive` 选择当前人物，非发言时段沿用模板已有状态。只补人物切换，不重做人物形象、音色和表演方法。

## 三、前端提交与 Render 怎么衔接

调用链保持：**两栏输入 → Analysis → 前端编辑完整分镜 → Render → 现有制作与交付**。

Render 已有接收前端 `dataList` 的能力，本次补齐字段传递和采用规则：

1. 前端提交对应的 `basePlanVersion`、本次完整 `dataList` 和当前 `otherRequirements`。人物、画面指令随分镜一起提交，服务不能再只取 `id/content`。
2. Render 以本次提交为制作基础，读取对应 Analysis 的原始两栏与初始分镜作为上下文。尊重当前镜头集合、台词、人物和顺序，不恢复用户已删内容。
3. `otherRequirements` 未传表示继承，非空表示本次要求，显式空串表示清空；不能用 `newValue || oldValue`。导演用要求补充未指定的画面、人物和风格；已经明确的字段与同次文字要求相互矛盾时，指出具体分镜和冲突内容。
4. 沿用现有分析版本校验、请求保存、任务恢复和幂等机制。正常导演规划继续在现有流程中完成，不新增制作计划登记操作或贯穿配音、审片、交付的另一套摘要。

实际工作台的源码位置需在开发时定位，改通分镜展示、编辑与提交入口；不能默认仓库中的 `apps/web` 就是正在使用的网页。前后端按最新接口一起更新，不增加旧协议兼容分支。

**服务内部落地顺序：**

1. **网页提交前**：前端保留 Analysis 返回的版本、分镜及导演字段；保存修改后提交完整列表，不只提交改动的几句。删除就是当前列表中不再包含该镜头，不从旧列表补齐。
2. **受理请求时**：`routes.ts` 继续调用 `normalizeWebRender()`，按显式 `basePlanVersion` 取得本任务对应的成功 Analysis，解析当前要求并保留全部已定义的分镜字段，再交给 `repo.accept()`。不使用任意字段透传代替正式 Schema。
3. **保存前完成归一化**：未传的 `otherRequirements` 从对应 Analysis 继承，明确传入的字符串原样采用，包括空串。这个处理发生在请求摘要计算和持久化之前；受理后的 Run 保存完整确定的请求，恢复时不再查“最新一版”重新拼输入。
4. **准备 Render 输入时**：`ProductionRunner.prepare()` 沿用当前 `request` 和已有 `analysis.result`，补充对应 Analysis 的原始两栏供导演参考。原始稿用于理解出处，当前 `dataList` 用于正文与顺序，不再另建编辑差异存储或计划登记工具。
5. **开始制作时**：协调技能把同一份当前输入交给导演和作者。画面要求落实到模板数据，台词落实到现有句段，指定人物落实到音色及人物状态；后续装配和检查读取这些已有对象。

**采用边界**：正文、镜头集合与顺序以当前 `dataList` 为准，要求改正文或已指定人物时，在现有分镜编辑区落实后提交；Render 不重新编写确认稿。字段未指定的部分由导演结合当前要求补充，风格、节奏和强调方式继续由导演理解。若结构化人物写甲、文字要求明确写乙且没有一致的当前结果，沿现有错误响应指出具体分镜，不在执行中悄悄覆盖已保存请求。

继承的 `otherRequirements` 按对应 Analysis 已记录的用途及采用关系理解：旧台词只作出处，已经采用的“第三段替换为……”等改稿指令不重复执行。持续性的风格和画面要求继续生效，正文变化仍以本次 `dataList` 为准。这直接复用 Analysis 结果，不再增加一份执行计划。

## 四、片头公司名与必要校验

**公司名**：从本次实际采用的标题或台词确定公司，保存对应依据；多家公司主次不明或没有公司时，`companyName=null`。编辑换题后重新核对，不能继续使用旧公司名。

**显示**：在现有片头指定区域增加独立文字层 `CompanyTitleOverlay`；空值不渲染文字或占位框。沿用原片头素材、时长、顺序和声音设置。

**具体实施：**

1. 导演在现有制作步骤中确定公司名及对应台词依据；只在内容足以确定时采用，不依靠模板默认公司或历史任务填充，也无需为公司名单独增加一次模型调用。
2. 在模板现有 `scene.intro` 数据上增加可空的 `companyName`，采用依据随当前制作记录保留；它是显示字段，不成为新的服务级制作计划。
3. 在 `FinancialDialogue.tsx` 已有片头 `Sequence` 内叠加文字层，共用片头起止范围，片头结束即隐藏。使用模板指定区域及文字换行规则，覆盖长公司名场景，不遮挡栏目固定元素。
4. 同步模板类型和校验，以及生成模板的维护脚本；通过生成的新模板包检查实际画面。只在候选目录手改一份 JSX 不算完成。

**配音检查**：正文有台词就按现有流程配音；模板片头按原素材播放；明确无口播画面按画面和时长处理。只在现有装配、时间线预检与句段核验中修正“一律要求每段有 TTS”的条件；无口播部分检查对应素材和时长，有台词却缺配音仍须报错，不以空白音频或改成无口播掩盖失败。无需因此另建通用声音来源系统。

| 实际内容 | 在现有代码中怎样处理 |
|---|---|
| 人物正文 | 保留配音句段、正文一致、音频文件、真实时长与字幕检查；缺一项仍报错 |
| 正文中插入模板片头 | 沿用已有 `scene.intro` 的素材与帧数；装配保留片头区间，口播与字幕避开该区间，不给片头虚造一句台词 |
| 独立无口播画面 | `kind=visual` 且正文为空、有画面安排与正时长时，允许本镜没有配音句段及口播字幕；按时长推进时间线，仍检查素材、边界和顺序 |

上述判断须在装配器、公共时间线预检、句段核验和切分检查中采用同一条件，不能只让其中一处放行。新增判断以请求中明确的无口播类型为依据，不能看到 TTS 结果为空就自动改类。若该次装配确实没有需配音的片段，应允许走已有素材及时长路径，不向供应商提交空批次；这只是消除接口假设，不扩展成独立的无声视频产品。

模板片头原有静音或原声设置保持当前代码行为，不因“支持无口播”顺带修改声音策略。全局动效与正文时序继续由现有作者和模板维护，不通过压短动画来完成这次适配。

### 技能与代码分别负责什么

| 承担方 | 本次负责 | 交给下一步的结果 |
|---|---|---|
| Analysis 技能与模板文字合同 | 综合两栏，识别台词、人物、动作及替换关系 | 结构化分镜及来源依据 |
| 输入/结果校验代码 | 检查两栏、版本、字段、来源引用和发言范围；保存完整数据 | 当前有效的请求或能定位的错误 |
| 前端编辑区 | 维护用户改后的台词、人物、画面说明及镜头集合 | 本次完整 Render 请求 |
| Render 协调、导演与模板作者 | 按当前分镜安排画面，拆自然句段，填入人物和公司文字 | 现有模板时间线及句段对应关系 |
| 既有配音、装配和预检工具 | 生成所需配音，接回实际时长，校验绑定与合法无口播范围 | 现有制作数据，继续进入原审片与导出流程 |

技能维护源只改 `.agents/skills/_shared/template-production/analysis.md`、`references/analysis.md`、Render 协调入口及 `references/director.md`、`references/scene.md`、必要的 `references/audio.md`。同时更新 `task-instructions.ts` 和模板生成的文字合同，避免一个入口仍要求朗读标签。结构校验、字段拼装、范围计算交给代码，不让各技能再各自解析一遍原稿。

### 本次开发的接续顺序

1. **先定义共同字段与校验**：Analysis 结果和 Render 请求共用分镜 Schema，明确来源、人物和无口播条件，避免前后端各有一份解释。
2. **接通输入与前端回传**：完成双栏 Analysis、分镜编辑、明确版本和当前要求传递；先证明当前分镜能完整进入已保存请求。
3. **接入现有制作**：完成句段人物切换、片头公司文字和必要的无口播条件判断，沿原工具生成时间线。
4. **同步说明与模板发行**：更新维护源、生成模板和插件副本，检查实际构建内容一致。
5. **完成增量验证并统一交付**：记录改动和通过的检查；所有步骤属于同一次开发，不拆成多批需求或多轮用户审批。

## 六、验证与排查

| 场景 | 通过标准 |
|---|---|
| 只填一栏、两栏同时填写，包含重复或明确替换内容 | 能正确分析；实际台词采用完整，替换有依据，人物和画面说明保留 |
| 指定人物、亮相标签、普通括号台词 | 说话人正确；导演标签不被朗读；真实台词不误删 |
| 前端改句、换人、删镜、重排、拆并多人对话 | 当前完整分镜进入 Render；人物范围有效，旧台词和被删镜头不恢复 |
| 当前要求未传、替换或清空；同任务多次 Analysis | 按本次要求和明确分析版本执行，不猜版本、不恢复已清空要求；旧改稿指令不重复执行 |
| 有公司、无公司、编辑换公司 | 片头文字正确，空值无占位，原片头播放保持不变 |
| 正文夹模板片头、明确无口播画面、有台词但缺音频 | 只为实际台词配音；合法片段能通过素材及时长核验；必要配音缺失仍报错 |
| 最新接口的普通正文任务 | 沿现有制作、审片、导出与自动交付流程正常完成 |

**检查落到现有测试和实际模板上：**

- `production-web-contract`、`production-http`、`production-analysis-boundary`、`production-flow`：覆盖双栏输入、标签分离、来源检查、新字段往返及 Render 上下文；不能仅以提示词包含关键词作为通过依据。
- `production-repository`：沿用已有身份与幂等逻辑，确认新增字段被保存；相同提交复用原 Run，人物或分镜实际变化被识别为新输入。
- `production-audio-assembly`、`production-timeline` 及现有句段/切分测试：检查多人句段对应、纯画面时长连续、切分范围正确，以及普通口播缺音频仍失败。
- `scripts/verify-finance-template.mjs` 与生成后的实际模板：核对同镜换人、公司名有/无/换题、长名称，以及片头前中后的显示范围；检查渲染画面，不能只看 JSON 有值。

测试只覆盖本次增量和实际受影响的回归，普通任务沿原流程跑通即可。既有审片能力不重新开发，不增加试听验收；文档更新本身不代表这些测试已执行。

输入不足或当前修改冲突时，沿现有错误响应指出缺项或具体分镜；素材、配音缺失沿现有任务错误与恢复机制处理。排查时先对照**本次提交 → Analysis 版本 → 分镜人物/指令 → 实际配音与片头绑定**，不另建排查系统。

本轮交付为运营需求及落地方案；代码、原提速方案和既有验证记录不在本轮修改范围。后续开发记录实际提交、修改文件与测试结果，部署和作品生成分别记录。
